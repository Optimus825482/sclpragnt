# Taste — Engineering

- Expects changes to be complete and error-free end-to-end ("eksiksiz, hatasız ve tam olarak") — backend, frontend, and supporting infrastructure updated together, not partially, and each batch verified with the full test suite (261/261) plus typecheck/build before reporting done. Confidence: 0.9
- Asks for performance optimization of both backend and frontend — both when features are added and as standalone system-wide audits: DB layer (connection/locking, query patterns), all background loops and intervals, concurrency/task management, per-module flow functions, and frontend polling/re-render. Confidence: 0.85
- Wants versioned/cache-busted frontend assets after UI changes so a browser refresh loads the new CSS instead of stale cache. Confidence: 0.8
- Keeps the SQL schema migration in sync with columns the code INSERTs/SELECTs; when new columns are added, applies them idempotently to already-existing tables (CREATE TABLE IF NOT EXISTS plus ALTER TABLE ... ADD COLUMN IF NOT EXISTS) so runtime code never crashes on a missing column. Confidence: 0.8
- Approves replacing the single global DB connection + global lock with a proper connection pool (`psycopg_pool`) that lets parallel DB operations run on separate connections — accepting the added dependency and a full rewrite of the connection layer, as long as multi-statement transactions keep their integrity (advisory locks / single-connection ops) and the change is proven by the full test suite. Confidence: 0.9
- Considers "print()" output inside background loops a log-pollution problem; wants high-frequency per-tick/per-symbol debug prints converted to leveled logging (logger.debug/info) while rare startup/one-off prints may stay as-is. Confidence: 0.8
- When requesting a full-system review, places special emphasis on calculations and algorithms ("özellikle hesaplamalar ve algoritmaları") — wants formula correctness, numeric edge cases, and cross-module consistency of indicators (same EMA/RSI/score computed differently in live vs. backtest vs. frontend) flagged, not just structural/schema bugs. Confidence: 0.7
- Decided the application no longer needs an integrated backtest engine and requested it be removed entirely ("backtest'i tamamen kaldır, gerek yok") now that the system runs live — deems in-app backtesting unnecessary; standalone research/replay scripts may remain untouched. Confidence: 0.8
- When a fix intentionally changes behavior, updates the tests asserting the old behavior to the new contract (e.g., stale PROCESSING-order FAILED threshold 30s→120s, `_start_background` call sites switched to factory/callable form) rather than reverting the fix — the suite must come back fully green with the contract change migration-retry source-contract assertions re-anchored from the old `range(1, 13)` strings to the new `_MAX_ATTEMPTS = 20` / advisory-lock / sha-marker contract) rather than reverting the fix — the suite must come back fully green with the contract change documented in the commit message. Confidence: 0.75
- Expects deploy-time scripts (DB schema migration in particular) to tolerate overlap with the live production system instead of failing fast: session-level `pg_advisory_lock` so parallel migration runners queue up, generous `lock_timeout` plus bounded patient retries (~10+ min) for transient error classes (LockNotAvailable, deadlock, connection), a fresh connection per attempt, and one idempotent `IF NOT EXISTS` transaction. A short fail-fast `lock_timeout=5s` in the container entrypoint caused a `LockNotAvailableError` restart loop during deploy because the still-running old container held table locks. Such scripts are validated locally before pushing with two consecutive runs against the local PostgreSQL (first applies and writes the marker, second must skip) plus the full test suite. When patient retries alone proved insufficient in production (a long ACCESS SHARE holder — the backup container's startup `pg_dump` — kept blocking every attempt), the preferred structural fix was a no-op fast-path: a `schema_sha256` marker written in the same transaction as the DDL so an unchanged schema skips DDL entirely on restarts (a pure read, no lock race), with the same sha guard mirrored in application-side `init_db()`. Confidence: 0.8

- Financial metrics shown to the user (average buy cost, current P/L on held positions) must reflect the actually-held position's real cost basis (FIFO inventory: deduct sold quantity from the oldest buys, average only what remains) — not a naive weighted average of ALL historical fills. The user caught that the displayed avg cost (~0.30) contradicted the actual last-buy price (~0.544) and made P/L look inflated (~113% instead of ~18%), i.e., "satıp tekrar alma" sequences must not drag the cost basis down artificially. Confidence: 0.7
- Keeps heavy/long-lock background jobs out of startup and deploy windows: the auto-backup container was re-gated from `postgres: service_healthy` to `depends_on: backend: condition: service_healthy` plus a 300s initial delay, because a startup `pg_dump` (minutes of ACCESS SHARE on every table) starved deploy-time migration DDL (which needs ACCESS EXCLUSIVE) into lock-timeout. Structural prevention of lock races is preferred over relying on retries alone. Confidence: 0.7

- The nginx gateway config must stay immune to container recreation: every deploy recreates the backend/frontend containers so their Docker IPs change, while nginx caches the IP resolved at startup forever — healthy backend inside (health 200, migration fast-path skipping) but "no available server"/502 from outside. Structural fix: `resolver 127.0.0.11 valid=10s ipv6=off` + `resolver_timeout 5s` with `set $upstream`-variable `proxy_pass`, so hostnames re-resolve per request — chosen over the operational workaround of restarting the gateway after every deploy. (Deployment topology: Coolify/Traefik terminates TLS and proxies to the nginx gateway container fronting backend:8004 and frontend:3004. Domain→service routing is defined per-service in the Coolify UI and materializes as Traefik labels only on redeploy; if the domain isn't attached to the gateway service, Traefik serves its own signature 404 — `text/plain` + `X-Content-Type-Options: nosniff` — even with every container healthy, so that header combo on an outer 404 means "no Traefik router for this Host", not an app error.) Confidence: 0.8

- Coolify/Traefik routing needs network membership, not just labels: even with the correct Traefik labels on the gateway (Host rule + Let's Encrypt certresolver), Traefik only discovers containers attached to its own Docker network — a gateway left only on the app's compose network creates no router at all, giving the same outer 404 / "no available server" while everything is healthy inside (diagnosable via `docker inspect ... .NetworkSettings.Networks`). Permanent fix: gateway service gets `networks: [default, coolify]` plus a top-level `networks: {coolify: {external: true, name: coolify}}` in docker-compose.yaml so every deploy attaches it automatically — the structural fix preferred over repeating a manual `docker network connect` after each deploy. Compose/config changes are validated locally before pushing (a yaml.safe_load parse check), same discipline as migration scripts. Production follow-up: Coolify's deploy attaches the gateway to the coolify network itself — `docker network connect coolify <gateway>` failing with "endpoint with name ... already exists in network coolify" is confirmation it is already attached, not a problem; if the Traefik 404 persists anyway, the next suspect is leftover/duplicate gateway containers from failed-partial deploys carrying identical router labels — enumerate with `docker ps -aqf name=gateway` (name/status/started-at/networks) and check `docker logs coolify-proxy --tail` for duplicate-router lines, keep only the newest container, then restart coolify-proxy. Confidence: 0.8

- When a container misbehaves despite the repo config looking correct, verifies what the LIVE running container actually has before theorizing further: `docker inspect ... --format '{{json .Config.Healthcheck}}'` on the running container, `docker exec` probes inside it (listening ports via netstat/ss/nginx process, grep of the mounted/generated config, wget of the health endpoint), and suspects a stale image (the repo/commit updated but the redeploy not yet loaded) as the cause when the in-container config matches the desired one yet the behavior is wrong. Confidence: 0.7

- Container healthchecks must measure the service's own liveness, never proxy to an upstream dependency: the gateway's healthcheck hit `/health`, which nginx forwards to the backend, so every gateway→backend hiccup flipped the gateway to `unhealthy` — and Coolify/Traefik then pulled it from rotation, turning a downstream outage into a total front-door 503 ("no available server") even though labels/networks/routing were all correct. Structural fix: a dependency-free self-check endpoint in nginx (`location = /gateway-health { return 200 "ok"; access_log off; }`) with the compose healthcheck pointed at it. General rule: a healthcheck that depends on another service cascades one service's failure into removal of the otherwise-healthy front layer; `(unhealthy)` in `docker ps` status is the first signal to check what the healthcheck actually probes. Confidence: 0.75
- Coolify-managed compose projects cannot be manipulated directly on the host via the path in the container's `com.docker.compose.project.config_files` label: that value (e.g. `/artifacts/<id>/docker-compose.yaml`) is a virtual path inside the Coolify controller, not a real path on the server, so `docker compose -f <that path> up -d --force-recreate` fails with "no such file or directory". With the repo config already correct and the running image current, the safe remediation for a stale/`unhealthy` Coolify container is the Coolify UI **Redeploy** (which re-creates it from the controller's own stored config) rather than a manual `docker rm` + `docker run`, which risks dropping the container's mounts/env/healthcheck config. Confidence: 0.7
- When a container healthcheck that probes `localhost` fails with "Connection refused" while probing `127.0.0.1` for the same service succeeds, suspect the container's `/etc/hosts` mapping `localhost` → IPv6 `::1` while the service only listens on IPv4 (`0.0.0.0`): wget resolves `localhost` to `::1`, finds nothing listening on IPv6, and fails. Permanent fix is to point the healthcheck/endpoint at `127.0.0.1` explicitly (in the compose healthcheck or `/etc/hosts`), not to chase the container state. Confidence: 0.7
- Next.js standalone containers must bind all interfaces or loopback healthchecks fail permanently: Next 16's `server.js` binds only to the `$HOSTNAME` env value, which inside Docker defaults to the container's own internal IP/hostname (e.g. `172.28.0.5:3004`) — so it is listening on NO loopback address. Signature: `docker exec ... ss -tlnp` shows a single `172.28.x.x:3004` LISTEN line and no `0.0.0.0`/`127.0.0.1` line; healthcheck probing `localhost:3004` gets "Connection refused" forever → `(unhealthy)` → Traefik/Coolify pulls the frontend → gateway timeout, even though the app serves fine on its container IP (verify with `wget --spider http://<container-hostname>:3004/` → OK). Permanent fix: `ENV HOSTNAME=0.0.0.0` in the frontend Dockerfile so Next binds every interface including localhost, and point the compose healthcheck at `127.0.0.1:3004` (IPv6-loopback-safe). This is distinct from the IPv6 `::1` pitfall — here the service isn't on ANY loopback. Confidence: 0.7
- Even a correct, dependency-free healthcheck can leave the container permanently `(unhealthy)` if its start_period is shorter than the time the service needs to bind its listen socket: diagnostic signature is the health log (`docker inspect ... --format '{{json .State.Health}}'`) showing startup-race "wget: can't connect to remote host: Connection refused" and "timed out starting health check" + a climbing FailingStreak, while the SAME endpoint answers fine (200/OK) when probed manually via `docker exec ... wget` — proving the endpoint works and the fault is the healthcheck racing the socket up. Fix: raise start_period above the service's bind time, then wait a full interval for the streak to reset to healthy — and remember the deployed image may still be stale (new config present in container but old image running), so verify against the live container before concluding. Note: this production Docker engine does NOT support in-place healthcheck edits — `docker update --health-cmd/--health-start-period` fails with "unknown flag" (and a bare `docker update` on a health field is unsupported), so the immediate-recovery band-aid must instead be a fresh container recreate (`docker compose -f <config> up -d --force-recreate --no-deps gateway`, which resets the `unhealthy` health state without touching dependent services) or a Coolify UI Redeploy, then re-check `docker ps` for `(healthy)` and the outer `curl -skI` for 200. Confidence: 0.7
