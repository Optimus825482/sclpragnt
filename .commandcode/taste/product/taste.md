# Taste — Product direction

- Prioritizes signal quality, profitability, and capital efficiency over trade count: false signals and positions that sit stagnant (capital-locking, "turtle"-like symbols) must be filtered, but filters should be developed via backward replay so profitable trades are minimally affected. Confidence: 0.9
- Wants LLM commentary focused on the near-term future ("ne olacak") and kept concise; predictions should be recorded to the DB and later scored for accuracy so the system can learn from its own past calls (self-learning loop). Confidence: 0.85
- Prefers consolidating related screens into one page with tabs, and clear at-a-glance visual states — PnL in green/red, bullish/bearish arrows per timeframe, and symbol×timeframe status grids whose cells are color-coded by direction (the requested MACD MONITOR page shows each active symbol's M1/M3/M5/M15/M30/H1 histogram as green/red cells plus a per-symbol green count). Confidence: 0.8
- Wants monitoring tables to layer a second, comparative dimension on top of direction, all within the same existing table (not a separate view): for the MACD MONITOR's green symbols, asked to surface ADR-based trend/momentum strength either by shading the green arrows by strength tier (GÜÇLÜ/NORMAL/ZAYIF) or by adding a min-max-normalized 0-10 strength score ("yeşil okları renk tonunu ayarlasak ya da ADR değerini normalize ederek 10 üzerinden gösterseydik ... aynı tabloda"). Deliverable pattern: color-tone intensity for the tiered signal + a numeric "GÜÇ · 0-10" column with tier chips and tooltips showing the raw ADR % — so the strongest green movers stand out at a glance and every column is explained via tooltip/legend. Confidence: 0.6
- Is a short-horizon scalper on the monitoring side: explicitly wants multi-timeframe strength aggregation weighted by their trading focus rather than averaged equally — M5/M15 leading ("M5'te sıçrama yapabilecekleri veya düzenli yukarı gidebilecekleri monitörlemek istiyorum"), H1 important but secondary/context, and M1/M3 downweighted as short-term noise ("M1/M3'ün ağırlığını azaltalım"). Requested concrete weights: M5=1.5, M15=1.4, H1=1.1, M30=1.0, M3=0.6, M1=0.4 — so an M5/M15 mover ranks high despite M1 wobble, while a brief M1 green flash alone cannot produce a high score. Confidence: 0.8
- Separates "trend strength" from volatility in what the monitoring GÜÇ/strength score should mean: the user itself flagged the just-delivered ADR-based strength as conceptually wrong for trend strength ("adr yerine adx kullansak trend gücünü ölçmek için daha iyi olmaz mı") and asked for a measure more sensitive than MACD and better than ADX/ADR for the same monitoring-page logic. On learning ADR only captures directionless daily-range (volatility) size, immediately accepted replacing it with a 20-bar linear-regression composite — |slope|/mean-bar-range (unit-free speed, comparable across symbols) × R² (consistency), averaged across M1..H1 and min-max normalized to 0-10 within the active universe — keeping the MACD histogram purely as the green/red direction layer (direction and strength stay separate signals, tooltips show the raw R²/speed). Shows no sunk-cost attachment: a metric shipped earlier in the same session is freely reworked once its semantics are clarified. Confidence: 0.65
- Wants user-facing monitoring/dashboard pages built with the user experience in the foreground: minimal technical jargon, plain-language status labels (balance, free balance, PnL, success/win-rate), and at-a-glance tracking rather than dense technical detail ("kullanıcı deneyimini ön planda tutarak çok fazla teknik detay içermeyen ve kullanıcıya net bilgi veren"). Confidence: 0.85
- Expects monitoring surfaces to update in near-real-time — open positions must reflect live current price and PnL dynamically (e.g., the "AÇIK İŞLEMLER" list under the chart) rather than being static/stale between infrequent polls, and standalone live monitors are explicitly demanded to be tick-driven/instant ("tick bazlı anlık güncellenen" for the MACD MONITOR page — satisfied with ~1 s WebSocket refreshes plus a REST fallback poll). Confidence: 0.75
- Wants monitoring/dashboard features visible to BOTH regular users and the admin (added to the shared/sidebar menus), not admin-restricted — e.g., the portfolio-monitoring page tracking the autonomous paper-trade system. Confidence: 0.75
- Sensitive/admin pages should support granular per-user viewer grants rather than a hard admin-only wall: requested that a specific named non-admin user (caner) get view access to the normally admin-only MACD MONITOR page while all other regular users remain blocked ("... kullanıcısının görüntüleme yetkisi verelim"). This implies a reusable per-page viewer-allowlist model (admin always passes; only listed usernames among regular users pass), expected to extend to more users/pages later rather than being a one-off hardcode. - Extends the push-alert expectation to the monitoring/scan layer itself (not only trade events): when a symbol's composite score crosses the alert threshold the user wants a WS event plus an OS push so they are notified without watching the screen ("ekrana bakmadan haberin olsun"). Confidence: 0.6
- Wants new trading-control features exposed as editable settings rather than hardcoded: delivered as a settings-panel section with an on/off toggle (default enabled), plus the key parameters as editable fields with sensible defaults — e.g., the trailing-stop module: "default olarak aktif", "%2 kara geçince fiyatı %0.8 geriden takip etsin", and "ayarlardan trailing modülü aktif/pasif yapılabilsin" — with the backend/config defaults, DB schema columns, and settings API all wired to the same flippable switch. Reconfirmed with a second feature: the "reopen after trailing/breakeven close" behavior was likewise required to be flippable from Settings via its own toggle (`reopen_after_protect_close`, default enabled) that gates the logic in `try_open_from_notification`, wired through config default → settings API editable list → settings UI dropdown — other exit reasons (take_profit/stop_loss/reset) remain hard-gated against reopening regardless of the toggle. The reopen condition later evolved: the original "price is trending up" check (price ≥ prior exit price) was removed at the user's request because it is inherently degenerate — a trailing/breakeven exit means price already fell from its peak to hit the stop, so the re-entry price is typically at/below the prior exit and the "rising" check always returns false, permanently blocking reopening. It was replaced with an explicit "target (take_profit) not reached" check: reopen when price stays above the notification price, the horizon hasn't expired, and the prior trade's take-profit was NOT reached (if already ≥ TP, don't reopen). That price/horizon condition was later dropped: reopen now keys purely off the monitoring page's latest "uygun adaylar" (suitable candidates) radar scan — as long as the symbol still appears on that list after a trailing/breakeven close, the position reopens immediately (rebuilding the notification from the cached candidate's price/score); once the symbol drops off the radar list, it does not reopen. Reconfirmed a third time for the MACD/sıçrama monitor layer: the user asked to move the SIRÇRAMA threshold into Settings and add a switch to completely kill OS push ("eşiği ayarlara taşıyalım ya da push'u tamamen kapatacak bir anahtar ekleyelim") — delivered as a dedicated Settings tab with a 0-100 threshold field, an alerts on/off toggle (WS event + in-page banner), and a separate web-push kill-switch. Channel semantics matter to the user: alerts off → nothing fires (score/list updates continue); push off → OS push stops but the in-page live banner keeps working. Wired as config defaults → DB-backed settings API (TTL-cached) → Settings UI, with the live threshold propagated into the snapshot consumed by both pages. Reconfirmed a fourth time when the user approved the staged "YAKLAŞIYOR → KIRILIM" early-signal (pre-breakout) alarm system with an explicit request that it ship active by default ("default olarak da aktif olsun") under its own settings key, rather than as an opt-in feature.
