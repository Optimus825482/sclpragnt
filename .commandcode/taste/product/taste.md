# Taste — Product direction

- Prioritizes signal quality, profitability, and capital efficiency over trade count: false signals and positions that sit stagnant (capital-locking, "turtle"-like symbols) must be filtered, but filters should be developed via backward replay so profitable trades are minimally affected. Confidence: 0.9
- Wants LLM commentary focused on the near-term future ("ne olacak") and kept concise; predictions should be recorded to the DB and later scored for accuracy so the system can learn from its own past calls (self-learning loop). Confidence: 0.85
- Prefers consolidating related screens into one page with tabs, and clear at-a-glance visual states (e.g., PnL in green/red, bullish/bearish arrows per timeframe). Confidence: 0.7
- Wants user-facing monitoring/dashboard pages built with the user experience in the foreground: minimal technical jargon, plain-language status labels (balance, free balance, PnL, success/win-rate), and at-a-glance tracking rather than dense technical detail ("kullanıcı deneyimini ön planda tutarak çok fazla teknik detay içermeyen ve kullanıcıya net bilgi veren"). Confidence: 0.85
- Expects position/monitoring tables in the dashboard UI to update in near-real-time — open positions must reflect live current price and PnL dynamically (e.g., the "AÇIK İŞLEMLER" list under the chart) rather than being static/stale between infrequent polls. Confidence: 0.6
- Wants monitoring/dashboard features visible to BOTH regular users and the admin (added to the shared/sidebar menus), not admin-restricted — e.g., the portfolio-monitoring page tracking the autonomous paper-trade system. Confidence: 0.75
- Expects monitoring alerts to reach the device as OS-level push notifications when the PWA is closed or backgrounded — in-app/WebSocket messages shown only while the app is open are not considered an adequate substitute ("PWA kapalıysa ya da arka plandaysa push notification olarak göstermiyor — neden?"; confirmed again when the user, on an installed Android Chrome PWA, found push_subscriptions empty and pushed for a fix; the user is again chasing a push-subscription failure on the installed mobile PWA). Confidence: 0.85
- On mobile wants a guided PWA onboarding funnel before push is expected to work: a confirm dialog when the browser is not Chrome (the system works best with Chrome), an "install as app" prompt when the PWA is not installed, and a notification-permission request after installation on opening the installed app — each step offering an explicit "don't show again" (kalıcı) vs. "later" (anlık) choice instead of endless nagging. Confidence: 0.85
- Expects the "BİR DAHA GÖSTERME" (kalıcı, localStorage) vs. momentary-dismiss two-tier pattern on every recurring modal — re-confirmed when requesting the login disclaimer. Confidence: 0.8
- Requires mandatory acknowledgment gates before regular (non-admin) users can use the panel — e.g., a checkbox-gated risk/liability disclaimer shown at login (TAMAM disabled until "Okudum, anladım" is checked); admin accounts are exempt from user-facing gates. Confidence: 0.8
- Wants user-facing disclaimer/modal copy kept short and to the point ("çok uzun olmayacak şekilde") even when the content is legally/technically dense (AI, automation bias, no-guarantee risk text). Confidence: 0.6
- Wants trade/history lists (e.g., the Binance TR "Günün İşlemleri" daily-trades table) sorted newest-first / descending by default, so the most recent buy/sell appears at the top ("en son alım/ satım en üstte, liste azalan olsun"). Confidence: 0.7
- Wants new trading-control features exposed as editable settings rather than hardcoded: delivered as a settings-panel section with an on/off toggle (default enabled), plus the key parameters as editable fields with sensible defaults — e.g., the trailing-stop module: "default olarak aktif", "%2 kara geçince fiyatı %0.8 geriden takip etsin", and "ayarlardan trailing modülü aktif/pasif yapılabilsin" — with the backend/config defaults, DB schema columns, and settings API all wired to the same flippable switch. Reconfirmed with a second feature: the "reopen after trailing/breakeven close" behavior was likewise required to be flippable from Settings via its own toggle (`reopen_after_protect_close`, default enabled) that gates the logic in `try_open_from_notification`, wired through config default → settings API editable list → settings UI dropdown — other exit reasons (take_profit/stop_loss/reset) remain hard-gated against reopening regardless of the toggle. The reopen condition later evolved: the original "price is trending up" check (price ≥ prior exit price) was removed at the user's request because it is inherently degenerate — a trailing/breakeven exit means price already fell from its peak to hit the stop, so the re-entry price is typically at/below the prior exit and the "rising" check always returns false, permanently blocking reopening. It was replaced with an explicit "target (take_profit) not reached" check: reopen when price stays above the notification price, the horizon hasn't expired, and the prior trade's take-profit was NOT reached (if already ≥ TP, don't reopen). That price/horizon condition was later dropped: reopen now keys purely off the monitoring page's latest "uygun adaylar" (suitable candidates) radar scan — as long as the symbol still appears on that list after a trailing/breakeven close, the position reopens immediately (rebuilding the notification from the cached candidate's price/score); once the symbol drops off the radar list, it does not reopen. Confidence: 0.8
- Wants exit rules to compose with clear precedence rather than race: once the trailing stop is active (or its trigger threshold is crossed), take-profit must NOT close the position — the trailing stop alone manages the exit even if price later reaches the original TP level ("trailing devreye girince TP'nin kalkması lazım"). The trailing trigger check must run before the TP check so TP never wins the race at/below the trigger level. Confidence: 0.7
