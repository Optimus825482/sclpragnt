# Taste — Infrastructure & ops

- The production Docker host runs many unrelated apps/services concurrently (Coolify/Traefik proxy plus numerous other projects' container stacks on the same host, some sharing ports). When fixing a fault in one app, the user explicitly wants the change scoped narrowly to that affected service so the rest of the network/apps are never disrupted ("o sunucuda çalışan bi sürü uygulamam var, komple networku bozmayalım") — prefer targeted operations (e.g., one service only, `--no-deps` recreate) over anything that touches the shared proxy, Docker network, or other containers. The user would rather have the assistant make the necessary docker-compose/config adjustments themselves than perform broad server-side network operations. Confidence: 0.7
- For disk/DB-growth problems, insists on MEASURING before deleting: the chosen path is always read-only diagnostics first (host `du -xhd1 /`, `docker system df`, Postgres `pg_database_size` / per-table `pg_total_relation_size` + live-vs-dead tuple counts, oldest-row dates), and the actual retention/deletion decisions are made from those real numbers rather than guesses — "tahminle silmek yerine önce ölçelim". The assistant is expected to run these via copy-pasteable commands the user executes (no direct server access) and to wait for the output before touching data. Confidence: 0.65
- Wants the application's Postgres data bounded by explicit retention windows instead of growing forever: historical candles + feature snapshots kept 21 days (ML training only looks back ~10 days, so older rows are dead data), and daily `pg_dump` backups kept 1 day instead of 7 on the disk-constrained host. Retention/pruning must cover ALL append-only telemetry tables (alerts, trace events, chat/memory logs), and deleting rows alone is not accepted as a fix unless space is actually returned to the OS (VACUUM). Confidence: 0.6
