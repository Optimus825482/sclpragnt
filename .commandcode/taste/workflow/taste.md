# Taste — Workflow & testing

- Requires every strategy/signal change to be validated empirically before going live: research → backtest/replay → compare against the current live strategy → only integrate if positive. Reconfirmed when the assistant proposed quantifying a design question (whether including the live/partial bar in the MACD `green`/`dip` decision causes intra-bar signal flicker vs. computing on closed candles only) before changing the code — the user's one-word go-ahead ("EVET YAP") sent it straight into an A/B simulation that measured the flicker rate before any fix was applied. Confidence: 0.95
- Wants each test to mirror the live strategy exactly (same SL/TP and rules) except for the single variable under test; runs separate tests per isolated change. Confidence: 0.85
- Rejects lookahead/hindsight analysis — evaluations must use only conditions measurable at signal time ("giriş anındaki ölçülebilir koşullar"), never reasoning from what happened afterward. Confidence: 0.8
- Prefers replay/backtest on historical data pulled from the public API (e.g., 48–72h) that reproduces live behavior, including which symbols would have been active at that time. Confidence: 0.75
- Wants quantitative comparison of variants and thresholds (e.g., score ≥3 vs ≥4, accuracy %, 15-min post-signal direction/move) rather than subjective verdicts. Confidence: 0.8
- Likes multi-timeframe pattern analysis of entry-time snapshots (M1/M5/M15/H1/H4) to find features separating profitable from losing trades before finalizing a rule set. Confidence: 0.85
- When the user reports a bug, expects a full-system health scan with a categorized report (real errors vs. data anomalies vs. healthy/normal items) rather than just patching the single reported symptom. Confidence: 0.7
- Proactively audits the entire application for errors, missing parts, and improvement areas — not just reacting to reported bugs, but hunting across backend, schema, frontend, ops, and tests in a single sweep. Confidence: 0.85
- Treats dependency security (CVE) / vulnerability scanning as part of the expected audit scope — wants CVEs explicitly covered and fixed, not left as a separate optional concern. Confidence: 0.7
- Delegates thorough analysis to parallel background agents covering different areas (backend, schema, frontend, ops) simultaneously, then synthesizes findings into one unified report. Confidence: 0.75
- Expects audit/fix findings to be grouped/ranked by category (critical errors → security → structure/cleanup → ops) for organized presentation, but then wants ALL items completed regardless of priority or order — explicitly tells the assistant not to ask which items or what sequencing to start with ("sırası benim için önemli değil, hepsini uygula"; earlier: "tamamını düzelt"). This extends to explicitly-flagged large/risky architectural changes (e.g., DB layer rewrite from single-connection+lock to a connection pool with a new dependency) — no extra per-item confirmation needed. Each finding is expected to be addressed and verified (full test suite + build) in one pass. Confidence: 0.95
- When comparing two of their own systems/features, wants a structured tabular report: a side-by-side comparison matrix PLUS separate per-system tables covering strengths, weaknesses, and improvement areas ("karşılaştırmalı tablo ve ayrı ayrı tablolar olarak raporla"). Confidence: 0.7
- Iterates in an audit → implement fixes → re-audit cycle: after making their own updates to the code, asks the assistant to review the changes "in the same way" — checking git history/diff to see what changed, verifying which previously-reported issues are now fixed vs. still open, and auditing the new code for newly-introduced bugs in the same categorized report format. Confidence: 0.7
- When presented with a (possibly stale) audit/weakness list, expects each item to be verified against the current code and triaged (already fixed / partially handled / still valid / deliberate design choice) before patching — does not re-fix already-solved items, and asks for explicit confirmation before touching intentional design decisions. Confidence: 0.75
- Prefers to export production data as SQL dump files and analyze them locally (loading into a local SQLite/DB) rather than granting the assistant direct access to the live database. Confidence: 0.6
- When synthesizing parallel-agent audit findings into the final report, first personally verifies the critical claims (reads the cited code/files itself — e.g., re-checking .env, .gitignore, the flagged component — rather than trusting the subagent) and runs the validation commands before publishing; the report leads with a "Doğrulanmış Durum" (verified/proven status) section, every finding carries concrete file:line evidence, and agent findings are written to be factual ("be specific and factual — do not speculate without code evidence"). Confidence: 0.75
- Development shell is Windows: Unix-only utilities (e.g., `tail`) are unavailable in command pipelines (they make validation commands fail), and background shell output capture can return empty logs even on success — run validation commands (pytest, npm typecheck) in the foreground without Unix pipes instead of piping through `| tail` or relying on background output files. Confidence: 0.75
- A fix round is expected to end with the changes committed and pushed without further prompting — the user's fix instruction itself includes the closing step ("SONRA DA COMMIT + PUSH YAP"). One consolidated commit with a detailed sectioned body (Kritik / Backend / Frontend / Altyapı + a doğrulama/verification summary line) written in ASCII-only Turkish (no Turkish special characters, avoiding git/Windows encoding issues), plus a Co-authored-by trailer. This holds for standalone hotfix rounds too (e.g., the deploy lock-timeout incident), each pushed as its own commit with the same detailed ASCII-Turkish body and trailer. Confidence: 0.9
- Steps that cannot be safely automated are not attempted unilaterally: server-side operational actions (writing the real SCALPER_SESSION_SECRET to the server's .env, DB/admin password rotation) and risky repo operations (git history rewrite / force-push to purge leaked secrets) are left as an explicit "Sana Kalan" (remains for you) list with warnings, instead of being silently skipped or executed without permission. Confidence: 0.7
- When a failure lives at the server/proxy layer (outside the repo and beyond the assistant's reach), the round is closed with a compact ordered diagnostic playbook the user can run on the server: numbered copy-paste commands (docker ps -a status table, docker exec wget probes of backend/frontend from inside the gateway, docker logs --tail) each paired with its interpretation branch (containers missing/restarting → check Coolify build logs; unreachable but Up → paste gateway logs; nginx [emerg] line → paste it for an immediate fix). Confidence: 0.7
- The deploy loop is log-driven: after each redeploy the user pastes the raw server startup/runtime log (full output, noise included, no commentary) and expects the assistant to root-cause from the logs alone — including spotting regressions introduced by its own previous commit that the local test suite did not catch, and latent bugs that only surface in production logs (e.g., an undefined `logger` NameError inside the push-delivery except block killing all push deliveries) — fix minimally, verify, push, and close with a short "redeploy again" instruction plus a status summary (what succeeded / what failed), rather than asking clarifying questions. Reconfirmed across consecutive cycles in one session (strategy-loop `list | set` TypeError fix, then the alerting.py logger fix), each closed the same way. Reconfirmed again in a later session when the user pasted a raw PostgreSQL retention-sweep log (two DB errors: an `embedding_jobs` timestamptz-vs-epoch type mismatch and a missing `strategy_scan_logs` table) with no commentary — the assistant root-caused from the log, fixed minimally (EXTRACT(EPOCH) cast, dropped the missing table), verified 272/272 tests, pushed a detailed ASCII-Turkish commit, and closed with "Deploy edip kontrol et" + a category-summary. Confidence: 0.85
- Fixes to live-infra faults ship in two tracks within the same round: an immediate server-side remediation command the user runs without redeploy (e.g., `docker network connect coolify <gateway>`, effective within seconds via Traefik's Docker-event watcher) for instant recovery, plus the permanent fix committed and pushed to the repo (compose/config) so the manual step never has to be repeated — closed with the ordered command/interpretation list and a short recap of everything fixed across the session. Confidence: 0.75
- Fix work is organized into numbered batches (W1…W{N}) with a fixed documentation + verification protocol, and each batch is expected to be documented and proven, not just committed: a `FIX_W{N}_<konu>.md` report is written into the audit output directory (`outputs/denetim_<tarih>/`) covering the finding→fix table, the verification evidence, and an explicit "bilinçli davranış değişiklikleri" (deliberate behavior changes) section; the batch ships a dedicated lock-test file (`tests/test_w{N}_*.py`) whose tests are named after the audit finding IDs; and a mutation verifier script under `scratch/` reverts each fix one at a time to prove the corresponding test actually breaks (raw output persisted to `scratch/w{N}_mut.txt`) — a green test alone is explicitly NOT accepted as proof ("yeşil test ≠ korunan davranış"; a test that passes even with the fix reverted is treated as vacuous and rewritten to exercise the real race/edge). Each batch closes with the full backend suite green plus the mutation tally (e.g. "50/50 mutasyon yakalandı"). Confidence: 0.7
- Trusting the existing fix plan is not enough — a separate coverage audit is expected that maps EVERY audit finding ID to the batch that closed it or the documented reason it remains open (`KALAN_GOREVLER.md`), because findings that no batch was ever assigned to (e.g. high-severity DB/runtime items) otherwise silently escape; the stated lesson is "kapsam denetimi, düzeltme planına güvenmekten daha güvenlidir". Partially-done batches (tests written but source not implemented, broken helper call-sites, a referenced-but-missing verifier) are detected and finished rather than reported as done. Confidence: 0.75
- Runs post-hoc gateway health checks as a recurring habit: saves the gateway's log output as a .txt file in the project root and asks the assistant whether there is a problem ("şu logu inceler misin, gateway'de sorun var mı gene") — expects a verdict on whether action is needed, where transient startup races (initial 502s while the backend is still booting), client-closed 499s, stale-frontend-chunk 404s, and harmless noise (e.g., repeated "duplicate header" warnings) are identified as non-issues rather than triggering fixes. When reporting a recurring intermittent fault (app runs fine a while → gateway error → restarting the Coolify proxy fixes it), the user pastes MULTIPLE components' logs at once (gateway + backend + postgres .txt dumps) and expects cross-component triage: state explicitly whether the fault window is even covered by the provided logs, rule each layer in/out with evidence (single clean backend boot, no ERROR/Traceback, no per-minute request gaps in the gateway), and — when all captured layers look healthy — point to the missing evidence needed for the real root cause (the Coolify/global proxy's own log, `docker events`/container restart times) rather than declaring the app healthy without caveat. Confidence: 0.7

- Distinguishes ANALYSIS rounds from FIX rounds: when asked to "analyze / examine / detect / report" (analiz et … tespit et … raporla), the expected deliverable is detection only — subagents are explicitly constrained to READ-ONLY (no source edits; each writes only its own report under the output folder, plus scratch proof scripts), and the round closes by proving the repo source is untouched (e.g. `git status --porcelain -- backend frontend` returning 0) before offering the fixes as a separate next step. Confidence: 0.65
- Includes an independent RED-TEAM verification agent in audit rounds: a separate agent that does not trust code comments or prior reports, re-derives the highest-risk numeric/semantic behaviour empirically by running the real functions, and returns a VERDICT per claim (CONFIRMED / PARTIAL / REFUTED) with the exact script + output as evidence — claims are only accepted if actually executed. Confidence: 0.6
- Numeric/semantic audit claims must be empirically proven, not argued from reading code: agents are told to import the REAL functions and patch only I/O, run them via the project venv (`venv\Scripts\python.exe` from the backend dir), quote actual outputs, and write the proof scripts under a `scratch/` subfolder of the output directory rather than in the repo. The synthesis report states the red-team tally (e.g. "28 iddia → 21 doğrulandı, 2 kısmi, 5 reddedildi") and lists clean/verified areas separately from findings. Confidence: 0.65

- Runs the parallel-background-agent protocol defensively against turn limits: each delegated subagent is told to work in the stated priority order, to WRITE ITS REPORT EARLY and keep updating it so partial progress is captured, and not to stop to ask questions; when an agent still exhausts its turn limit, the main assistant does NOT relaunch it — it measures the actual repo state itself (git status, does the promised file/test exist, `py_compile`) and the full test suite, then completes the missing pieces by hand and drives everything back to green before reporting. Confidence: 0.65
- For large fix rounds the parallel delegation is organized into conflict-free WAVES partitioned by FILE OWNERSHIP: each subagent is given an explicit allowlist ("you may ONLY edit X, Y, Z; do NOT edit any other file — if a fix needs another file, implement your half behind a stable interface and REPORT the needed change") and the cross-agent CONTRACTS it must expose or respect are spelled out verbatim (e.g. the exact new config key + default, the new POST endpoint + flags, the helper function another agent will call), so several agents can fix backend/frontend simultaneously without touching the same file. Confidence: 0.6
- When several fix agents run concurrently, verification is scoped rather than global: each agent runs `py_compile` on its own files plus only its own new test file and the existing suites for the modules it owns, and is told NOT to chase unrelated failures because other agents are editing other files at the same time; the full backend suite + `tsc --noEmit`/`next build` green check belongs to the main assistant's closing step of the round. Confidence: 0.55
